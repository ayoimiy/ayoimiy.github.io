> 这个页面目前是结构预览，不包含完整的法术数值。  
> 在数据来源、游戏版本和字段定义稳定之前，不会用看起来精确的表格代替可验证的引用。

## 为什么要先定数据结构

一个法术条目可能包含：

- 游戏内名称与内部 ID；
- 法术类型、元素、法力消耗；
- 施法延迟与充能影响；
- 伤害、爆炸半径、速度、生命周期；
- 是否可被特定修正影响；
- 与其他法术或材料的交互；
- 版本差异与来源。

如果一开始就把它们塞进一张宽表，之后每加一个字段都会破坏排版。更稳妥的顺序是：

1. 定义最小字段集；
2. 找一份可以核对的游戏版本；
3. 用脚本从数据文件或手工记录生成页面；
4. 给每个数值标注来源和版本；
5. 最后再做筛选器和计算器。

## 计划字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 内部标识，保持稳定 |
| `name` | string | 游戏内显示名称 |
| `name_en` | string | 英文名称，便于交叉引用 |
| `type` | enum | 投射物、静态投射物、材料、其他 |
| `mana` | number | 法力消耗 |
| `cast_delay` | number | 对施法延迟的影响 |
| `recharge` | number | 对充能时间的影响 |
| `damage` | number | 基础伤害，注明类型 |
| `speed` | number | 初速或速度倍率 |
| `lifetime` | number | 生命周期 |
| `tags` | string[] | 元素、用途、交互标签 |
| `game_version` | string | 数据对应版本 |
| `source` | string | 数据来源与采集方式 |
| `notes` | string | 例外、歧义与待验证项 |

## 页面生成路线

第一版不手写几百个页面。更可行的路线是：

```text
数据文件（JSON/YAML）
        │
        ├─ 校验：字段缺失、重复 ID、版本冲突
        │
        └─ Astro 内容集合 / 动态路由
                │
                └─ 法术详情页 + 索引表 + Pagefind 搜索
```

这样每次游戏更新后，只需要更新数据与差异记录，而不是逐页修改 Markdown。

## 数据来源的规则

- 优先使用当前游戏版本的 `data/` 文件或官方工具输出。
- 社区 Wiki 可以作为交叉验证，但要记录访问日期和页面版本。
- 不直接把 Wiki 的大段内容复制进本站；引用时注明来源与许可。
- 对同一字段出现冲突时，保留冲突，不擅自“平均”两个数值。
- 任何“实测值”都要带测试条件，否则只能算一次观察。

- 确定内部 ID 与游戏内名称的映射；
